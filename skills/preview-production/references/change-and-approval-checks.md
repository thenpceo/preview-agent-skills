# Change and approval checks

Read before changing production structure, replacing shared content, promoting references or recording approval. These checks support authorized work; they do not require repeating permission for an exact change the user already specified.

## Inspect and propose the smallest change

Read the target canvases/shotlists/sequences/items, library variations, current takes, notes, assignments and decisions. Save before snapshots for a bounded migration/replacement. Identify exactly what will be created, reused, modified or retired.

An unused template placeholder needs generic naming AND default/example content AND supporting history/context. A planned sequence with no media is established work. A default name with meaningful notes, assignments, images or reviews is established work too. If uncertain, ask.

| Situation | Agent action |
| --- | --- |
| User specifies sequence names/order; only confirmed untouched placeholders exist | Briefly explain the mapping and adapt within setup authorization. Preserve useful IDs and verify names/order/counts. |
| A lead created a meaningful sequence, canvas, breakdown or library entry | Reuse when appropriate. Ask before an unrequested replacement, rename, merge, move or restructure. |
| Exact change to established work is explicitly approved | Apply that delta without asking again; preserve unrelated fields/history. |
| A project's categories differ from this skill's preferred script → milestone hierarchy | Recommend the structure when relevant; do not migrate established categories just to match the skill. An authorized category migration moves existing canvases by ID and preserves groups, manual geometry, media, review records and approvals. |
| A matching record exists under another name | Resolve its purpose before duplicating; ask about reuse/rename only when ambiguity affects the task. |
| An addition would conflict or duplicate an approval queue | Prepare the concrete addition; confirm reuse, extension or separate deliverable. |
| Shared Notes, Script or selection changed since inspection | Re-read and reconcile; stop the conflicting overwrite. Do not remove a precondition to force a retry. |
| User requests migration, deletion or reset | Identify affected IDs, media/review relationships and recovery method. Obtain unresolved explicit decisions before removing meaningful work. Prefer verified copies/archives where appropriate. |
| User asks only for audit, plan, packaging or a hold | Keep live structure, approval, sharing and generation unchanged. Prepare reviewable artifacts. |

Examples:

- “A sequence named ‘Lookdev Frames’ has 12 planned shots and assignments. Should I extend it, or create a separate sequence for this deliverable?”
- “The rename of ‘Location A · Animation’ is explicit; I’ll rename that canvas and preserve its working groups.” This is an update, not a question when already authorized.
- “These entries appear to be the same character but have different variations. Should I reuse the existing identity or keep them separate?”

Do not disguise replacement as routine setup. Approval to overwrite the skill does not authorize later overwrites of production records.

## Configure approval authority

Record the reference approver, internal reviewer, final shot/creative approver and producer/release owner in the project guide or existing policy. Roles can share a person. Prefer existing evidence over asking again. Suggested arrangement: producer approves reusable references, internal lead checks candidates, director approves film shots, producer releases packages. This is an example, not evidence of current authority.

Approval evidence identifies exact item/take or attachment ID, variation/state, phase/purpose, version, brief validity, approving person/role, decision date and traceable source. An explicit decision from the designated approver in conversation, a review comment, or a documented meeting decision can qualify. Establish the requester's authority before treating their statement as the required approval. Do not require repetition of already available evidence.

If authority is missing, ask who owns that approval. If authority is known but the exact decision is missing, ask narrowly: “Has the producer approved this exact character version for the reference library, or is it still a candidate?” Approval of appearance/wardrobe does not approve later animation/performance.

## Draft metadata versus approved media

Creating a Character, Location or Prop placeholder is allowed during authorized setup. State that media/approval is pending and link it to the production items. Do not require approval just to name a draft identity.

Promotion into the canonical production reference set requires the configured reference approver's actual decision. Canvas placement, an artist's Final tag, provider completion or assignment to References does not satisfy this gate.

1. Verify the exact candidate, owning review item, intended variation and current decision. Reuse valid evidence.
2. If approval is missing, leave the candidate in its canvas/review item at Needs Review. Prepare the library mapping and ask for the missing decision; do not mark it approved or mix it into the approved set.
3. If explicitly asked to save unapproved exploration, keep it visibly draft/provisional and separate through supported folders/descriptions or the canvas. Storage is not approval. Do not invent library statuses, locks or fields.
4. Once approved, attach the exact source to the matching existing variation, retain its take/review link, and record the attachment mapping/evidence. Do not attach every group member.
5. Replacing/removing approved attachments needs a clear new-baseline decision. Preserve history and identify stale dependencies; do not infer permission to regenerate them.

Library membership is not an approval source. Use the owning review record and exact approved attachment map. Shared states are reviewed once and reused; intentional different states may be separately reviewed.

## Status and release checks

Normal path: To Do → In Progress → Needs Review → Internally Approved → Final Approved. Changes Requested and Blocked name the next action/owner; Archived is inactive history. Use actual project labels/IDs/native categories instead of silently rewriting menus.

- Artist submissions may set Needs Review within assigned work.
- Internally Approved requires the designated internal reviewer's exact-version decision.
- Final Approved requires the configured approver for that item type: references may need producer approval; film shots may need director approval.
- Revisions inherit neither decision. Record the new candidate separately and return it to Needs Review.
- A multipart shot's approval requires exact accepted coverage for every required A/B/C part. Map each required part to its selected take and decision in Notes; an optional/TBC part stays optional. Combining rows does not transfer a part's approval to another asset or establish a new decision.
- If feedback invalidates the previous take for the current brief, record its unsuitability while retaining historical evidence. Optional exploration need not invalidate a still-valid approval.

If one visible status cannot express both candidate review and an older valid approval, retain both IDs/decisions explicitly in Notes/select records. Do not claim a status toggle stores complete native approval history.

Verify required coverage and exact valid decisions before packaging a final approved release. A review deck may contain pending work when labeled. Agents may prepare packages; external transmission, sharing/invites and paid runs each need authorization for their own scope.
